## Intent
Probes the model's ability to write a migration guide for a real breaking-change surface spanning config schema, CLI, and a typed API, where several of the changes are dangerous specifically because they are silent default changes rather than removed/renamed identifiers that would fail loudly.

## Assumptions
- The reviewer should treat the "What changed, in detail" section as the complete and authoritative list of behavior changes; the guide should not need to invent additional breaking changes to be considered complete, but also should not omit any of the ones given.
- The reviewer is assessing documentation/communication quality (accuracy, completeness, usefulness to an upgrading engineer), not evaluating whether v3's design choices were good ones.
- A correct guide will surface that several changes fail loudly (compile errors, fatal config validation, removed CLI flags) while others are dangerous precisely because they do not fail at all (the `retry.max_attempts` default dropping from 25 to 10, and the `metrics.port`/`metrics.path` defaults changing) — a reviewer should specifically check whether the answer distinguishes these two categories rather than treating all changes as equally self-announcing.
- Rollback guidance should be judged on whether it is operationally realistic given what was described (e.g., pinning the previous version, restoring the old config format) rather than on inventing an in-place downgrade mechanism that was never described as existing.

## Reviewer notes
A strong answer is organized so an engineer under time pressure can act on it without reading every paragraph: a concise summary of what changed, followed by an ordered upgrade procedure, followed by the concrete before/after diffs. It explicitly flags the two silent-default changes (retry max attempts 25 to 10, metrics port/path) as more dangerous than the loudly-failing ones, because a team that changes nothing in their config will still experience different behavior after upgrading — this is the single best differentiator between a strong and weak answer. It also correctly identifies that the removed `concurrency` (global) has no direct v3 equivalent and must be redistributed across per-queue `max_workers` values, rather than implying a mechanical one-to-one rename. It notes that `--legacy-heartbeat` and `--queues` CLI overrides have no replacement flag and require a workflow change (editing/templating the config file, or accepting mandatory heartbeats), not just a renamed flag. A weak answer restates the config diff without explaining operational consequences, treats every change as equally severe, misses that some behavior changes happen even to teams who touch nothing, invents a config compatibility shim or automatic converter that was never described as existing, or gives rollback advice that assumes capabilities (like hot-swapping retry semantics) not established in the prompt.
