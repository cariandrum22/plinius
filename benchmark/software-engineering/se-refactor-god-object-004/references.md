## Intent

This benchmark probes a model's ability to perform structural refactoring of a god object under realistic constraints: a single method that interleaves validation, inventory mutation, discount computation, tax calculation, persistence, and notification, all inside one database transaction with a "best effort, never fails the order" side effect (email). It tests whether the model can (1) identify genuinely tangled responsibilities rather than just relabeling existing code blocks with new method names, (2) propose a decomposition with real dependency boundaries (what talks to the database, what is pure computation, what needs to be inside vs. outside the transaction, what must not be allowed to fail the overall operation), and (3) reason about the trade-offs of those boundaries rather than asserting a decomposition is obviously correct. It also tests whether the model preserves subtle existing behavior (coupon precedence over the bulk discount, rounding order, backorder handling that zeroes rather than decrements inventory, and swallowing email failures) instead of "cleaning up" behavior that looks accidental but is load-bearing.

## Assumptions

- The reviewer should treat `getTaxRateForRegion` and `sendEmail` as fixed, already-tested externals; a good answer does not need to redesign or mock their internals, only decide where calls to them live architecturally.
- The reviewer should assume the database schema and the public `PlaceOrderInput`/`PlaceOrderResult` contract are fixed; a decomposition that requires changing the RPC-facing signature or the schema should be flagged as a bigger change, not silently assumed.
- The reviewer should assume the existing transactional behavior (the whole inventory-check-and-reserve plus order/order-line insert happens atomically, with rollback on any failure before commit) is intentional and must be preserved by any proposed decomposition, even if responsibilities are split across multiple objects or modules.
- The reviewer should assume "no test suite beyond stale integration tests" is a real constraint: a decomposition that becomes meaningfully more unit-testable is a genuine improvement, not a nice-to-have detail.
- Assume the two queued features (per-customer promotional pricing, SMS notifications) are mentioned to let the reviewer judge whether the proposed seams actually make those additions easier, not as features to design in full.

## Reviewer notes

A strong answer names the specific tangles rather than generic complaints: it should notice that the inventory check-and-reserve loop, the discount computation, the tax computation, and the persistence calls all read and write shared local state (`subtotalCents`, `backorderedSkus`, `this.lastAppliedDiscountCents`) inside one control flow and one open transaction, and that `this.lastAppliedDiscountCents` being instance state (rather than a local return value) is itself a latent bug risk under any future concurrent use of a shared service instance. It should recognize the discount precedence rule as a real invariant to preserve (explicit coupon code takes priority; the 5% bulk discount only applies when no coupon discount was applied, not in addition to it) and should notice that a coupon lookup falls back to a DB query only for unrecognized codes, with two hardcoded codes handled without a DB round trip — a decomposition should make a deliberate, stated choice about whether to preserve or collapse that asymmetry, not lose it silently.

Strong answers propose seams along genuine boundaries — for example, distinguishing pure/computable concerns (validation, discount rules, tax arithmetic) from I/O-bound concerns (inventory reservation, order persistence, notification) and being explicit about which parts must remain inside the single database transaction versus which can safely run after commit. They should address where backorder detection semantics live and confirm the same "email never fails the order" isolation is preserved (e.g., a failure in the post-commit notification step must not roll back or error the overall call). They should give a reasoned answer to a genuinely debatable design question implicit in this code: whether the transactional orchestration (BEGIN/COMMIT/ROLLBACK, the row locking) belongs to a persistence-focused unit that the rest of the logic calls into, or whether the top-level orchestrator should own the transaction boundary directly while delegating pure computation elsewhere — either is defensible if the trade-offs (testability of the pure logic without a real database, versus keeping the transaction script narrow and legible) are actually discussed.

Weak answers rename methods or split the class into two or three pieces without changing the underlying tangle (e.g., a "PricingHelper" that still takes a live DB client and issues its own queries alongside pricing math), silently change discount precedence or rounding, move the coupon-code special cases in a way that changes behavior, expand or shrink the transaction boundary without acknowledging the consistency implications, or provide only a bulleted list of intended classes with no code concrete enough to judge whether the seams actually hold together. Also treat as weak any answer that "fixes" the email-swallowing behavior by propagating the error, or that changes how backorders are recorded, without explicitly flagging and justifying that as an intentional behavior change rather than an accidental one.
