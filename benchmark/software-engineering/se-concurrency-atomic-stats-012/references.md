## Intent

This benchmark probes a model's ability to identify and correctly reason about data races in idiomatic-looking Go code that nonetheless violates the language's concurrency safety rules, and to connect those races to two qualitatively different observed symptoms — a hard crash versus a silent, small numerical discrepancy. It also tests whether the model can compare standard remediation strategies (mutex, atomics, sharding) on their actual merits for this workload rather than defaulting to a single "always correct" answer regardless of context.

## Assumptions

- The reviewer should assume standard Go semantics: plain Go maps are not safe for concurrent use when at least one accessor is a write, and the runtime may (but is not guaranteed to) detect and crash on concurrent map writes/read-writes with a fatal error that is not recoverable; a plain `int64` field incremented with `x++` from multiple goroutines without synchronization is a data race and the increment is not atomic (it is a non-atomic read-modify-write sequence).
- The reviewer should assume the described production symptoms (occasional crash under load, and a dashboard total that undercounts real traffic without crashing) are both real and both attributable to the code shown, and that `go test -race` reliably flagging a race under concurrent simulation is accurate signal.
- The reviewer should assume a single `*Collector` instance is shared across all concurrently-running request-handling goroutines for the lifetime of the process, as stated, and that `Snapshot` can be invoked concurrently with in-flight requests at any time.
- The reviewer should assume the route set is low-cardinality (a handful to a few dozen distinct route patterns) and that request volume can be high, since this materially affects which remediation is preferable.

## Reviewer notes

A strong answer distinguishes at least two distinct races rather than treating "there's a race" as one undifferentiated finding: unsynchronized concurrent writes to the `byRoute`/`latencyNs` maps from multiple request-handling goroutines (a map-on-map race, which Go's runtime can detect and terminate the process for), and an unsynchronized, non-atomic increment of the plain `Total int64` field from multiple goroutines (a races-but-usually-doesn't-crash scenario where concurrent read-modify-write sequences on the same memory location can interleave and lose updates without any runtime detection, since ordinary integer fields carry no built-in safety check the way maps do). It should also note that `Snapshot`'s unsynchronized reads of the maps, running concurrently with the handlers' writes, are themselves racing reads-vs-writes, independent of the two write-side races just described.

The explanation should connect the crash symptom specifically to the map races: Go's runtime has an explicit, best-effort check for concurrent map writes (and concurrent read/write) that can trigger a fatal, unrecoverable "concurrent map writes" (or similar) runtime error when the timing lines up, which explains an occasional hard crash under load rather than every single request failing. It should connect the quiet undercount symptom specifically to the `Total++` race: two goroutines reading the same old value of `Total` before either writes back its incremented value results in one increment being silently lost, producing a final count lower than the true number of requests, with no crash and no error, which is consistent with a load test showing a small, non-obviously-attributable discrepancy rather than an outage.

For the fix, reward answers that correctly identify that a `sync.Mutex` (or `sync.RWMutex`, noting `Snapshot` is a read-heavy path that still needs to exclude concurrent writers) protecting all three fields is the simplest and safest baseline. A strong answer should also engage with `sync/atomic` as an option for the scalar `Total` counter specifically (noting atomics are a poor fit for protecting map access as a whole, since Go maps have no atomic API of their own, so atomics alone cannot fully replace synchronization for the map fields), and with sharding (e.g., per-goroutine or striped counters merged on `Snapshot`) as a way to reduce lock contention under very high concurrency at the cost of more complex merge logic and slightly stale/inconsistent reads unless carefully coordinated. Given the stated low route cardinality and the fact that `Snapshot` runs only every 15 seconds, reward answers that reason explicitly about whether the added complexity of sharding is actually warranted here versus a straightforward mutex, rather than reaching for the most elaborate option by default. Penalize answers that only fix one of the races (e.g., wrapping the map writes but leaving `Total++` unguarded, or vice versa), that claim `sync/atomic` alone fully solves the map race without qualification, or that misattribute the crash to something other than the concurrent map access (e.g., a nil map, which is not the case here since both maps are initialized in the constructor).
