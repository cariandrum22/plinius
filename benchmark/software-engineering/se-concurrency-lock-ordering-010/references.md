## Intent

This benchmark probes a model's ability to diagnose a classic but easy-to-miss concurrency defect: a deadlock arising from two independently-owned locks acquired in inconsistent order across two subsystems that call into each other. It specifically tests whether the model can (1) trace lock acquisition order along two distinct call paths and recognize the circular-wait condition precisely, rather than vaguely invoking "deadlock" without pinpointing the mechanism, (2) connect the intermittent, load-and-schedule-dependent symptom profile to the underlying race for lock acquisition order, and (3) reason about a structural fix at the level of subsystem design and API boundaries, not just a local patch, including a realistic discussion of the trade-offs among competing fixes.

## Assumptions

- The reviewer should assume standard Go `sync.Mutex` semantics: a non-reentrant mutex where a second `Lock()` call by any goroutine (including the one already holding a different mutex) blocks until that mutex is released, and Go provides no built-in deadlock detection for goroutines blocked on mutexes (unlike an all-goroutines-asleep panic, two goroutines blocked while others could still run will not be flagged automatically).
- The reviewer should assume the described production symptoms (paged twice, full unresponsiveness, restart required, goroutine dump showing exactly two blocked goroutines with 0% CPU) are accurate and diagnostic, not red herrings.
- The reviewer should assume the reconciliation goroutine and the API-triggered transfer path are the only two call paths that touch these two locks, and that both are triggered concurrently and repeatedly under normal operation.
- Assume no code beyond what is shown is relevant to the defect (e.g., no other method on either type acquires both locks).

## Reviewer notes

A strong answer will name both locks explicitly (the `AccountManager` mutex and the `TransferService` mutex) and show that `Transfer` acquires them in the order account-lock-then-log-lock (via the call into `recordTransfer` while still holding the account lock), while `Reconcile` acquires them in the reverse order, log-lock-then-account-lock (via the call into `GetBalance` while still holding the log lock). It should state plainly that this is the textbook AB-BA lock ordering hazard: if one goroutine has acquired the first lock in its order and is waiting for the second while another goroutine has done the reverse, neither can proceed and both block forever, which matches the goroutine dump (two goroutines, each holding one lock and blocked acquiring the other, both idle rather than spinning).

It should explain why this is intermittent: the deadlock only occurs when the two call paths interleave within a narrow window — specifically when a `Transfer` call has acquired the account lock but not yet completed `recordTransfer`, at the same instant `Reconcile` has acquired the log lock but not yet completed its call to `GetBalance` for the same or a colliding pair of resources. Under low traffic or when reconciliation happens to run between transfers rather than concurrently with one, the two goroutines never contend for both locks at the same moment, so the program appears correct for long stretches. The correlation with peak traffic and the reconciliation minute follows directly from this: more concurrent transfers and a running reconciliation both increase the odds of hitting the narrow interleaving window.

For the redesign, reward answers that reason about the problem as one of establishing an invariant no future code can violate by accident — such as a strict, documented global order for acquiring these two locks (and enforcing it structurally, e.g., by never calling into the other subsystem's public API while holding your own lock, or by using a mediator/queue so state mutation and cross-subsystem notification are decoupled), rather than answers that merely suggest "add a timeout" or "retry on failure," which do not eliminate the underlying hazard and would just convert a hang into a lossy, hard-to-debug failure mode. Strong answers weigh at least one credible alternative (e.g., copying out the balance under one lock and releasing it before calling into the other subsystem, or merging the two locks into one if the subsystems are tightly coupled enough that independent locking offers little real concurrency benefit) and are honest about what is given up under each option — code coupling, reduced parallelism, or increased risk that a future contributor reintroduces the same hazard by adding a new cross-call under a held lock. Penalize answers that misattribute the hang to unrelated causes (e.g., the map access patterns, or missing nil-checks) without addressing the two-lock ordering issue, or that propose a fix that only works for the specific method pair shown without addressing the general discipline needed to prevent recurrence.
