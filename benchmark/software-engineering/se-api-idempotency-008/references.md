## Intent

This benchmark probes a model's ability to design an idempotency contract for a distributed, multi-instance API endpoint whose side effect (charging a card through a non-idempotent third-party processor) is expensive to get wrong. It specifically tests whether the model can (1) distinguish a legitimate retry from a key-reuse conflict via request fingerprinting rather than trusting the key alone, (2) reason about the race window when two requests carrying the same key arrive concurrently across multiple stateless instances, (3) specify what "replaying" a response actually requires (returning the same resource identity and outcome, not just "a" successful-looking response), and (4) reason about failure ordering between the non-idempotent external call and the durable record of the idempotency key, since that ordering determines whether a crash mid-request produces a double charge, a silently lost charge, or a safely retryable state.

## Assumptions

- The reviewer should assume the service runs as multiple stateless instances behind a load balancer, so any in-memory-only mechanism confined to a single process instance does not provide a real guarantee.
- The reviewer should assume `s.processor.Charge` is a genuinely non-idempotent external call that this team cannot modify or make idempotent themselves, and that it is the only step in the handler that has an irreversible real-world effect (moving money).
- The reviewer should assume clients may retry after any timeout, connection failure, or 5xx — including cases where the original request actually succeeded server-side but the response never reached the client — so "the client never got a response" cannot be assumed to mean "the server never finished."
- The reviewer should assume idempotency keys are supplied by the calling storefront per logical charge attempt (e.g., scoped to an order), not generated or controlled by this service.

## Reviewer notes

A strong answer treats the idempotency key together with a fingerprint of the request's meaningful parameters (not the key alone) as the basis for deciding whether a request is a safe retry or a genuine conflict, and specifies what the server should do in the conflict case. It gives a concrete mechanism for the concurrent-arrival race — some form of exclusivity (such as a uniqueness constraint or lock acquired before the external call) that ensures at most one attempt actually reaches the processor for a given key, with a defined behavior for the request that loses the race (wait for the result, or receive a well-defined "in progress" signal, rather than proceeding independently). It defines response replay precisely: a retried request must receive the original resulting resource (same charge identity and status), not merely a request that is re-processed and happens to succeed again. Critically, it reasons about the ordering between calling the processor and durably recording that the key has been used, and confronts the fact that a crash between those two steps is possible — a strong answer acknowledges this window explicitly and either narrows it as much as is feasible or specifies a reconciliation approach, rather than presenting a design that only works if nothing ever fails between the two steps. It should also justify a storage backend and expiry window appropriate to the domain (long enough to cover realistic client retry windows, but bounded) rather than treating storage as an afterthought.

Weaker answers rely on the idempotency key alone with no fingerprint check (so a key reused with a different payload is silently treated as a duplicate), assume a single in-process cache or lock is sufficient without acknowledging multiple instances, describe "replay" vaguely as re-running the handler, or never address what happens if the process crashes between charging the card and recording that fact.
