## Intent

This benchmark probes a model's ability to diagnose and remediate a classic but consequential performance defect: an N+1 query pattern hidden behind an ORM's lazy-loading relationship traversal and a serializer that appears declarative and harmless. It tests whether the model can (1) trace serializer field access back to the underlying ORM queries it triggers, distinguishing what the initial queryset actually fetches from what is lazily resolved per related object, (2) connect that mechanism to why the defect scales with result-set size and was invisible under light test data, and (3) reason about remediation with genuine engineering judgment rather than reflexively naming "eager loading" without weighing its costs (memory, over-fetching, cache staleness, write-path complexity).

## Assumptions

- The reviewer should assume standard Django ORM and Django REST Framework semantics: accessing a `ForeignKey` attribute or an `all()`/`related_name` manager on a model instance that was not eagerly loaded issues a new query at access time, once per instance.
- The reviewer should assume the described production telemetry (query counts, DB CPU, connection-pool pressure, APM time attribution) is accurate and representative, not a red herring.
- The reviewer should assume the models and views shown are the complete relevant surface for this defect — there is no upstream caching layer or middleware already mitigating it.
- Assume the page size cap (50 orders) and the observation that queries scale with page content, not with the cap, are both correct and worth reconciling in the diagnosis.

## Reviewer notes

A strong answer identifies precisely which accesses in the serializer are the source of extra queries: the `customer.name` access on each order, the `items.all` traversal on each order, and the `product.sku`/`product.name`/`product.unit_price` access on each item — and explains that the initial queryset only fetches the 50 `Order` rows themselves, with every related `Customer`, related `OrderItem` set, and related `Product` resolved lazily and individually as the serializer walks the object graph. It should articulate why the query count is a function of orders-times-items rather than a fixed number, and why this was undetectable in staging with a handful of seeded orders but severe in production with deep order histories and concurrent load — small per-query latency multiplied by a large and variable number of round trips, compounding under concurrency into connection-pool contention.

Strong answers name and compare genuinely different remediation strategies rather than treating "add select_related and prefetch_related" as a single trivial fix with no downsides — for example, distinguishing straightforward eager loading from more surgical approaches using `Prefetch` with restricted/projected querysets, or denormalization/caching for read-heavy fields, and should reason honestly about what each costs: increased memory per request from eagerly materializing related rows, the risk of over-fetching columns or rows never used by the response, added complexity if the eager-loading query plan itself becomes a large join or multiple prefetch queries, and staleness or invalidation complexity if a cache is introduced instead of or alongside eager loading. A strong answer also proposes a concrete way to measure query count and latency before and after (rather than asserting improvement) and a way to prevent regression as the codebase evolves. Penalize answers that only gesture at "use select_related" without identifying which specific relationships need it and why, that ignore the items-level N+1 while only fixing the customer-level one (or vice versa), or that propose a fix without any means of verifying it actually reduces query count.
