## Intent

This benchmark probes a model's ability to design property-based tests for a pure function whose correctness space is far larger than any hand-picked set of examples can cover, and where the domain (financial allocation) makes rounding/conservation errors materially costly. It specifically tests whether the model can (1) derive precise, checkable invariants directly from the domain requirements rather than restating the implementation in words, (2) design realistic input generators that actually exercise the interesting corners of the input space (skewed weights, zero weights, large recipient counts, boundary totals) rather than only "random small integers," (3) reason honestly about the oracle problem — how you check a property without silently re-deriving the function under test — and (4) articulate, concretely, what property-based testing buys over example-based testing here, and where it is not a full substitute.

## Assumptions

- The reviewer should assume `total` and `ratios` are supplied by callers within the same codebase (not directly from untrusted external input), so the interesting test surface is correctness across the space of *valid* inputs, not input sanitization.
- The reviewer should assume "correct" is defined by the domain requirement stated in the prompt: the parts must always sum exactly to `total`, must be non-negative integers, and should track the given `ratios` as closely as integer rounding allows — not by any single hidden reference implementation the reviewer is expected to know in advance.
- The reviewer should assume ratios may include zero (a recipient entitled to no share), very large disparities between ratios (e.g. one ratio orders of magnitude larger than another), and recipient counts ranging from one up to large values (hundreds or thousands), since these are realistic in the stated use cases (invoice line items, cohabiting accounts, refund distribution).
- The reviewer should assume standard IEEE-754 double-precision arithmetic is used for the intermediate ratio/fraction computations (as JavaScript/TypeScript numbers), so floating-point representation and comparison behavior is a legitimate concern, not an out-of-scope implementation detail.
- Assume the reviewer is evaluating test *design* quality (properties, generators, oracle reasoning, and comparative bug-class analysis), not requiring runnable code with a specific property-testing library, though code using a library such as fast-check is welcome if the reasoning is sound.

## Reviewer notes

A strong answer states invariants precisely enough to be executable assertions, going meaningfully beyond "the parts should sum to the total" as a single throwaway line. Expect properties covering conservation of the total, non-negativity and integrality of every part, and some notion of proportional fidelity relative to the ideal (unrounded) share — stated in a way that is falsifiable and specific about the bound of acceptable rounding deviation per recipient, rather than left vague. Reward answers that also consider properties tied to permutation and scaling behavior (e.g. what should and should not change if ratios are reordered, or scaled uniformly) if raised thoughtfully, but do not require every conceivable property to be enumerated.

On generators, reward designs that deliberately bias toward the corners of the space that are likely to expose bugs — many recipients, zero-weight recipients, highly skewed weight ratios, totals at or near zero, and totals that are not evenly divisible — rather than uniform small-integer generation alone, and that give a coherent account of what a well-shrunk minimal failing example should look like (e.g., the smallest recipient count and simplest weight ratio that still reproduces a given class of failure), since shrinking quality is what makes a property-test failure actually debuggable in practice.

On the oracle question, a strong answer confronts the real difficulty directly: for a property like "sums to total," the check is trivial and needs no oracle beyond arithmetic, but for a property like "as proportional as possible," the answer must explain how correctness is judged without merely restating the function under test in different words — for example, via an independently justifiable bound derived from the math of the allocation problem itself, or via cross-checking against a separately reasoned reference method, and should be candid about where an oracle is genuinely hard to construct. Penalize answers that quietly assume an oracle exists without addressing how it is obtained, or that treat "run the function and check it doesn't throw" as a meaningful property.

On the comparative analysis, reward answers that give concrete, plausible bug classes property-based testing would catch here (e.g., off-by-one remainder distribution under large recipient counts, floating-point edge cases with skewed ratios, a rounding rule that occasionally allocates a negative or duplicate index) versus what it would not reliably catch (e.g., a fixed, well-known regression at one specific historical input, or defects only observable through integration with a specific caller's data shapes) — the goal is a specific, well-reasoned comparison, not a generic "properties are more thorough than examples" claim.
