## Intent

This benchmark probes a model's understanding of `asyncio` task lifecycle and cancellation semantics beyond surface familiarity with `asyncio.wait`/`gather`/`wait_for` syntax. It specifically tests whether the model recognizes that a timeout on a wait primitive does not, by itself, terminate the tasks being waited on; whether it can trace what "leaked" tasks actually do (keep running, hold resources, eventually complete or fail with nobody listening); whether it can identify a specific place where errors are being discarded rather than merely being handled; and whether a redesign correctly accounts for all three distinct exit paths a fan-out-with-deadline coroutine can take (deadline expiry, an upstream error, and external cancellation of the coordinator itself) rather than only the happy path or only the timeout path.

## Assumptions

- The reviewer should assume standard `asyncio` semantics: `asyncio.wait(..., timeout=...)` returns the sets of completed and still-pending awaitables without cancelling or otherwise acting on the pending ones — the caller is responsible for deciding what to do with tasks left in `pending`. A `Task` that is never explicitly cancelled and never awaited continues running independently on the event loop until it completes or raises, and if its result/exception is never retrieved, `asyncio`'s default handling for tasks whose exception was never retrieved is only a logged warning (not something the tested code even provides), not a caller-visible error.
- The reviewer should assume the described production symptoms (a growing number of live, request-unassociated tasks under sustained slow-upstream load; complete production-log silence for weeks about a real, recurring malformed-JSON bug in one upstream) are accurate and are both explainable from the code shown.
- The reviewer should assume `session` is a genuinely shared, long-lived HTTP client session reused across many concurrent requests, so resource cleanup for an individual fetch must not assume it owns exclusive access to connection-level resources the way a private client would.
- The reviewer should assume the outer framework can and does cancel the `load_dashboard` coroutine's own task on client disconnect, and that this is a real, recurring event in production traffic, not a hypothetical edge case.

## Reviewer notes

A strong answer will state plainly that `asyncio.wait` returning after its `timeout` elapses does not cancel or stop anything in `pending` — those tasks (created eagerly via `asyncio.create_task` before the wait) keep executing independently on the event loop after `load_dashboard` returns its result, since nothing in the function ever calls `.cancel()` on them or awaits them again. It should connect this directly to the profiling symptom: under load with a slow upstream, a meaningful fraction of requests hit the deadline while one or more fetches are still outstanding, and each such occurrence leaves an orphaned task running to completion (or hanging) with no remaining reference tying it back to a request, which is exactly what accumulates as "live tasks not associated with any active request." It should also address the cancellation-of-the-coordinator case: if the caller's task running `load_dashboard` is itself cancelled (client disconnect) while inside the `await asyncio.wait(...)` call, the `CancelledError` propagates out through `load_dashboard` immediately — and, just as in the timeout case, none of the three fetch tasks it created are cancelled as a result, since `asyncio.wait` does not link the cancellation of the caller to the cancellation of the awaitables passed into it the way some structured-concurrency constructs do.

For the swallowed-error diagnosis, a strong answer will point specifically to the bare `except Exception: continue` inside the loop over `done`, noting that it discards the exception entirely — no logging, no metric, no re-raise — so a task that completed with a JSON-parsing error looks, from the outside, identical to a task that simply hasn't been checked, which is why a real and recurring upstream bug produced zero signal in logs despite affecting live traffic.

For the redesign, reward answers that ensure every exit path — deadline hit, an individual fetch raising, and external cancellation of `load_dashboard` itself — leaves no task still running when the function returns or propagates its own cancellation, typically by explicitly cancelling and awaiting (with cancellation exceptions suppressed) any tasks not yet complete before returning, in every case including the propagating-cancellation case (not only the deadline branch). Reward answers that surface individual fetch failures observably (logged with enough context to diagnose, even if the dashboard still degrades gracefully for that section) rather than silently discarding them. Reward explicit, reasoned engagement with the trade-off between returning a best-effort partial dashboard on timeout (better perceived latency and availability, at the cost of occasionally serving incomplete data silently unless clearly signaled to the caller/renderer) versus treating any timeout as a full failure (simpler correctness story, worse availability), and with the trade-off between manual `create_task`/`cancel`/`gather`-with-`return_exceptions` management versus newer structured-concurrency constructs (e.g., a task group that ties child task lifetimes to the enclosing scope) that make "no orphaned children" a structural guarantee rather than something each call site must remember to implement. A strong answer should also note that because `session` is shared, cleanup must not close or otherwise mutate shared connection-level state on cancellation of a single fetch — only the fetch's own task/awaitable should be cancelled, not the underlying session. Penalize answers that only add a `try/except CancelledError` around the whole function without cancelling the child tasks, that assume `gather` or `wait_for` alone (without also handling the child tasks explicitly on every exit path) is sufficient, or that fix the logging gap but leave the task leak unaddressed.
