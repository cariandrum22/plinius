## Intent

This benchmark probes a model's ability to diagnose and remedy primitive obsession in a Java service under a realistic constraint: three distinct, previously-occurred incident classes (identifier transposition, unit confusion in a percentage value, and cross-currency amount mixing) that a stronger type system could plausibly prevent. It tests whether the model can (1) map each incident to a precise type-level root cause rather than offering a generic "use value objects" answer, (2) design value objects with real, justified invariants and appropriate encapsulation rather than thin wrapper classes that just rename `String`/`long`/`double`, and (3) give an honest assessment of which incidents become compile-time-safe versus which remain only runtime-checked after the refactor, since not all three incident classes are equally solvable by typing alone.

## Assumptions

- The reviewer should treat `LedgerClient` as a fixed, already-tested external boundary; a good answer may add adapter/mapping logic to call it from new types, but should not need to change its own method signatures.
- The reviewer should assume the validation behavior currently performed by `validateId`, `validateCurrency`, `validateAmount`, and `validatePercentage` is intentional and must still be enforced somewhere after the refactor — it does not need to remain in those exact private methods, but blank ids, unsupported currencies, negative amounts, and out-of-range percentages must still be rejected.
- The reviewer should assume the discount/fee arithmetic itself (`computeShare`, using `BigDecimal` for the percentage multiplication and truncating via `longValue()`) is correct as written and should be preserved exactly, including its rounding behavior, unless the model explicitly argues for and flags a deliberate change.
- The reviewer should assume gRPC handler call sites elsewhere in the codebase currently construct calls from raw protobuf-derived primitives, so any answer that introduces value objects must address, even briefly, how those call sites are expected to adapt.
- Assume the three named incidents (id transposition, percentage unit confusion, cross-currency amount mixing) are the concrete evidence the reviewer should hold the model's design accountable to — a good design should be evaluated primarily against whether it plausibly prevents recurrence of these three, not against an open-ended wishlist of type-safety improvements.

## Reviewer notes

A strong answer distinguishes what a nominal/branded identifier type actually buys (distinct types for `AccountId`/`MerchantId`/`InvoiceId` make an accidental swap a compile error, since two different types can't be silently substituted for each other by the compiler even though both wrap a `String`) from what a `Money`-style value type buys for the currency-mixing incident (bundling amount and currency together, and having any arithmetic or transfer operation on `Money` require or check matching currencies, makes mixing amounts from two currencies fail loudly rather than silently producing a wrong number). It should also correctly identify that the percentage-unit incident (raw fraction `0.1` passed where whole-percent `10` was expected) is the hardest of the three to make a true compile-time error out of a bare `double`, since both a fraction and a whole-percent value are structurally identical `double`s — the strongest treatment introduces a dedicated `Percentage` (or similar) type with named, unambiguous construction (e.g. distinct factory methods for "from whole percent" versus "from fraction," or a single canonical unit enforced at construction with validation), and should be honest that this converts the bug from "silently wrong money" to "a loud runtime validation failure or an explicit, harder-to-misuse construction API," not necessarily to a compile error, unless the model argues for a more elaborate scheme (e.g. separate types for fraction vs. whole-percent) and reasons about whether that added complexity is worth it.

Reward designs where each value object enforces a genuine invariant at construction (non-blank/well-formed ids, a currency validated against the supported set or an enum, a non-negative amount, a percentage within its valid range) rather than being a bare wrapper that still requires external validation calls scattered through the service, since that would just relocate the primitive obsession rather than fix it. Reward honesty about migration costs: more classes, constructor/validation boilerplate, friction at the protobuf/gRPC boundary where primitives must be parsed into these types (and where invalid input first becomes representable), and the need for equals/hashCode or comparison semantics on the new types where relevant. A strong answer explicitly states which of the three incidents its design converts to a compile-time impossibility (typically the identifier transposition, if distinct types are used per id kind) versus which remain a runtime check that fails faster/louder/closer to the source than before (typically the cross-currency mixing and the percentage-unit confusion) rather than overclaiming that all three become "impossible."

Weak answers introduce a single generic wrapper type (e.g. one `Id` class reused for every kind of identifier, or a `Money` class that doesn't actually enforce currency-matching on its operations) that does not meaningfully prevent any of the three incidents, claim all three incidents become compile-time errors without justification, silently change the discount/fee rounding behavior, drop or weaken existing validation instead of relocating it into the new types, or provide only prose describing "a Money class and an AccountId class" without concrete code showing the refactored `BillingService` methods and how they call into the fixed `LedgerClient` boundary.
