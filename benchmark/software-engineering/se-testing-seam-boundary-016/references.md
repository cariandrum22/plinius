## Intent

This benchmark probes a model's ability to recognize why a class is untestable in isolation and to apply dependency inversion to introduce a testing seam without over-engineering the design. It specifically tests whether the model can (1) attribute each testability problem to its precise source in the code (direct construction of an HTTP client, a direct environment variable read, and a direct call to the system clock, all performed inside the method under test) rather than giving a generic "it has side effects" answer, (2) propose a seam at a sensible level of abstraction — one that isolates the business rules for testing without requiring the test to reimplement or stub out unrelated concerns, and (3) design unit tests that actually target the stated business rules (date window, minimum total, rounding, unknown code, fetch failure) with meaningful boundary cases, not just happy-path smoke tests.

## Assumptions

- The reviewer should assume `Promotion.fromJson` is out of scope and already correctly tested; the task is about the eligibility/orchestration logic in `PromotionEligibilityService`, not JSON parsing.
- The reviewer should assume the pricing API, the `PRICING_API_KEY` environment variable, and the system clock are all real external dependencies in production and cannot be removed from the system, only abstracted away from the class's direct control for testing purposes.
- The reviewer should assume "today" matters to the business rule (the promotion's active date window) and is not incidental, so any seam must still allow the production code to use the real current date when actually running.
- The reviewer should assume test code shown as scenario descriptions (setup/action/expected outcome) is an acceptable substitute for full Java source, since the task explicitly permits this format, and should not penalize the absence of literal `@Test`-annotated methods if the scenarios are precise and complete.
- Assume standard JUnit/Mockito-style tooling is available if the answer chooses to write literal test code, but assume no specific framework is mandated.

## Reviewer notes

A strong answer identifies all three distinct testability obstacles precisely: the method constructs its own `HttpClient` and builds a live outbound request inside `fetchPromotion`, it reads `PRICING_API_KEY` directly from the process environment, and it reads `LocalDate.now()` directly inside `evaluate`, and it explains that each of these hard-codes a concrete, real-world collaborator that a unit test cannot control or substitute. Reward answers that treat these as separable concerns (a test needing to control "what promotion data comes back" is a different problem from a test needing to control "what day it is") rather than proposing one change that conflates them without explanation.

A strong redesign inverts the dependencies so `PromotionEligibilityService` receives its collaborators rather than constructing them, at a boundary chosen to isolate the business rules being tested — reward designs that justify the level of abstraction chosen (e.g., abstracting "get me a Promotion for this code" as a whole, rather than only swapping out the `HttpClient`, which would still leave URL-building, header construction, and JSON parsing entangled with the test) and that separately address the clock dependency. Be skeptical of answers that abstract every single detail (e.g., introducing a full HTTP client abstraction layer, a separate JSON parser abstraction, and a configuration abstraction) without explaining why that additional layering is warranted for this class, since a good seam should be no larger than needed to make the business rules testable.

On the test scenarios, reward coverage that includes both edges of the date window (the start date and end date themselves, not just clearly-inside/clearly-outside dates), the exact minimum-order-total boundary (at, just above, and just below), a rounding case where naive rounding could plausibly differ from correct rounding, the unknown-promo-code path, and the fetch-failure path with attention to what the caller should observe (e.g., whether it should be a thrown exception, and whether that is distinguishable from "the checkout should not silently approve a discount it couldn't verify"). Penalize test lists that only cover the approval happy path and one rejection reason, or that never engage with what should happen when the promotion cannot be fetched at all. Finally, reward a justification of the seam boundary that engages honestly with at least one alternative (e.g., mocking at a lower level, or a different collaborator boundary) and explains the trade-off, rather than asserting the chosen design is the only reasonable one.
